# 本体驱动 NL2SQL 设计

## 目标

本体层解决三个问题：

1. 用户使用业务概念提问，不必先知道真实表名和字段名。
2. 模型能区分“业务上有关”和“SQL中可以安全关联”。
3. 表结构增加、字段改名或关系调整后，仍通过一个工作簿完成增量同步。

当前采用轻量业务本体，不引入完整 OWL 推理器。每个关系都必须能追溯到人工确认的状态和物理字段路径。

## 三层结构

### 业务实体层

`Entities`工作表定义用户实际谈论的对象，例如船舶、航次申报、船员申报、舱单货物和港口。

实体不依赖某一张物理表。一个实体可以由多个数据集的字段共同描述，一个数据集也可以同时承载多个实体。

### 语义映射层

`Fields`工作表把物理字段映射为：

- `entity_id`：字段属于哪个业务实体；
- `property_id`：字段表示实体的哪个属性；
- `semantic_type`：标识、名称、代码、时间、数量等语义类型；
- `semantic_role`：计划时间、实际时间、维度、度量等语义角色；
- `synonyms`：用户的常见叫法。

模型只使用真实字段引用生成查询计划，实体和属性用于理解问题和消除歧义。

### 物理执行层

`Relations`工作表只表达业务关系，不直接生成 SQL。关系状态分为：

| 状态 | 含义 | 是否允许 SQL JOIN |
|---|---|---|
| `verified` | 业务关系和物理路径均已确认 | 是，且必须通过全部结构校验 |
| `pending` | 业务上可能有关，但外键或粒度未确认 | 否，只能用于澄清 |
| `conflict` | 存在冲突定义 | 否，只能用于澄清 |

`JoinPaths`工作表保存经过确认的物理路径。只有`verified`关系可以配置路径，并且目标字段必须完整匹配目标表真实主键。

当前 SQL 编译器支持直接多对一和一对一关联。一对多、多对多和多跳查询保留在本体模型中，暂不生成 SQL。

## 当前数据本体

当前工作簿定义了五个实体：

- `ship`：船舶；
- `voyage_declaration`：航次申报；
- `crew_declaration`：船员申报；
- `cargo_manifest_item`：舱单货物明细；
- `port`：港口。

五个业务关系均暂为`pending`，因为现有字段清单没有证明以下关联：

- 航次申报通过哪个字段关联船舶；
- 船员申报与航次的外键；
- 舱单货物明细与航次的外键；
- 进口、出口上下港字段如何映射到港口字典主键。

在业务方确认并核验真实主键前，这些问题会触发澄清，不会生成跨表 JOIN。

## 当前查询链路

```text
自然语言问题
  → FAISS召回表、字段、实体描述
  → 组装候选数据集及其局部实体子图
  → 模型生成受限 QueryPlan
  → 编译器只使用已核验物理关系生成 JOIN
  → SQL AST校验
  → 达梦执行
```

规划模型收到的局部子图包含：

- 当前候选数据集的实体；
- 实体属性到字段的映射；
- 与候选实体直接相连的语义关系；
- 关系状态和已核验物理路径。

## 后续实现路线

### 阶段一：轻量本体目录

当前版本已完成：

- Excel本体维护；
- 实体和属性映射；
- 语义关系与物理路径分离；
- FAISS实体召回；
- Planner局部子图；
- `pending/conflict`关系禁止 JOIN；
- `verified`路径的目标主键核验。

### 阶段二：语义解析与图路径解析器

新增独立`OntologyResolver`：

1. 从问题中抽取实体、属性、时间、指标和筛选条件。
2. 使用别名、同义词、FAISS和精确匹配生成候选实体。
3. 根据`verified`关系搜索从主实体到目标实体的最短路径。
4. 限制最大跳数、路径数量和重复节点，防止图循环。
5. 将解析结果转换为现有`QueryPlan`，不把图谱直接交给模型自由编写SQL。

第一版路径搜索建议限制为最多3跳。无可用路径时返回`needs_clarification`，并指出缺失的关系或字段。

### 阶段三：完整语义约束

逐步加入：

- 时间语义：计划、实际、申报、更新时间；
- 指标语义：分子、分母、去重键、业务过滤条件；
- 枚举字典和代码系统一；
- 单位换算；
- 版本、生效日期、审核人和来源；
- 冲突关系的优先级与人工裁决记录。

指标仍由服务端编译，模型只选择已定义指标，不能自行设计计算口径。

### 阶段四：规模化和图存储

表数量较少时继续使用JSON本体和内存邻接图。达到以下条件后再考虑图数据库：

- 实体和关系达到数百至数千级；
- 多跳路径搜索明显变慢；
- 需要在线维护关系版本；
- 需要多人审核和关系治理；
- 需要按用户或业务域加载不同子图。

图数据库只负责确定性实体和关系，FAISS/Milvus继续负责描述和同义词的模糊召回。

## 变更流程

新增实体：

1. 在`Entities`增加实体定义。
2. 在`Fields`为相关字段填写`entity_id`和`property_id`。
3. 如需关联其他实体，在`Relations`增加语义关系。
4. 关联未确认时保持`pending`。
5. 执行`catalog-sync --excel configs/catalog.xlsx`。

确认关联：

1. 核实源字段、目标表和目标真实主键。
2. 在`JoinPaths`增加路径。
3. 将`Relations.status`改为`verified`。
4. 同步时程序重新读取达梦元数据并核验路径。
5. 核验失败时旧配置和旧索引保持有效。

## 验收标准

后续每增加一种本体能力，至少覆盖：

- 正常路径；
- 待确认关系；
- 冲突关系；
- 复合键关联；
- 目标主键缺失或不匹配；
- 关系循环；
- 多跳路径；
- 字段同义词召回；
- 时间角色和指标口径；
- 与手工SQL结果逐项比对。
